# Commit bodies are checked for what the changelog misreads (agent)

- release-it's parser (conventional-commits-parser 7, conventionalcommits preset) reads the whole message. It links every `#N` as an issue of this repo, and it reads every line after `BREAKING CHANGE:` into the note until a line that looks like a footer (`word: text`). raf-effect-atom 0.1.0–0.2.2 and effect-atom-boundary 0.1.0 shipped links to issues that don't exist (example-app ids, raf-query issues, React error #321), and 0.2.0's breaking note stopped at "returns a" because the next line began `promise: write`.
- `tooling/conventional-commits/src/message.ts` rejects both, in the `commit-msg` hook and the `Commits` workflow (which now reads `%B`, not `%s`). A `#N` (or `word#word`) may appear only in a `Refs:` / `Fixes:` / `Closes:` / `Resolves:` footer and as the subject's trailing `(#N)`. Code spans, URLs and `owner/repo#N` are fine. `BREAKING CHANGE:` takes one line, and only reference footers, `Co-authored-by:` and `Signed-off-by:` may follow it.
- It applies to every commit, not only those touching `packages/`: the hook doesn't know which paths will reach a changelog, and one rule is easier to follow.
- `message.test.ts` runs the real parser on the accepted messages, so a parser upgrade that reads them differently fails there. Keep its devDependency versions equal to the ones `@release-it/conventional-changelog` resolves.
- Lost: checking that each `#N` exists on GitHub. It needs the network in the hook and a token in CI, and an agent reaches for `Refs:` on purpose; the footer-only rule is documented instead. Indented continuation lines for a long breaking note are also out: the parser does keep them, but the note text keeps the indent, and one line is a simpler rule.
