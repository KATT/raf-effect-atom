# Boundaries claim by wrapping the atom (human chose, may revisit)

- **Call sites:** `useAtomResult(useIssueBoundary().wrap(issue(id)))` under a `createErrorBoundary` boundary, `useAtomSuspense(AtomErrorBoundary.claim(issue(id)), { suspendOnWaiting: true })` under an `AtomErrorBoundary`. `wrap` is `Atom.transform(source, …)` with `initialValueTarget` set to `source` afterwards, memoized per boundary and atom: a claimed failure becomes `Cause.die(error)`, recorded in the failed-reads WeakMap for `reset`. Its type is `AsyncResult<A, Exclude<E, { _tag: Tags }>>`.
- **No dependency between the packages.** `raf-effect-atom` has no claims overload and no `effect-atom-boundary` peer (only a devDependency for its integration tests); `effect-atom-boundary` has no read hook of its own.
- **`raf-effect-atom`'s `useAtomResult` follows `initialValueTarget`**, a generic Effect pointer, to the first serializable atom in the chain (the atom itself if it's serializable): it waits for the source's pending stream, builds the source node from `hydrated(source)` before reading the derived atom, and releases the lease on the source. Without that, hydration requests the atom again (always when streamed, and when settled unless the source node is built first). It returns typed failures and throws defects (`Cause.squash`), so a claimed error reaches the boundary as the error instance.
- **Costs accepted:**
  - Claimed typed errors are defects inside the wrapped value: `AsyncResult.error` returns `None`, and logs and devtools show a `Die`.
  - Plain Effect hooks on a wrapped atom need `suspendOnWaiting: true` (or they return the old failure while a reset refreshes), and request again after server rendering since they skip raf's hydration.
  - Two atoms per read: loaders start the source, components read the wrapper. The wrapper isn't serializable, so loader verbs reject it in development.
  - `AtomErrorBoundary.claim` claims every typed failure: the reader's errors are `never`, and a tag with no handler escapes as a defect to the boundaries above.
- **Gotcha:** `Atom.transform`'s own `initialValueTarget` option points at the end of the target's chain. An AtomRpc query with `reactivityKeys` is `serializable(withReactivity(inner))`, so that end is the inner atom with no serialization key, and a derived atom pointing there requests again after hydration. That's why `wrap` sets the pointer itself; raf's test fixtures use reactivity keys, as the apps do.
- **Rejected: a claims argument** (`useAtomResult(issue(id), useIssueBoundary())`) with `effect-atom-boundary` a peer of `raf-effect-atom`. Fewer moving parts and errors stay typed in the value, but it binds the packages together and needs a read hook per package.
- The spike that compared them drove the full server → wire → hydrate → boundary pipeline; its results are in this file's commit body.
