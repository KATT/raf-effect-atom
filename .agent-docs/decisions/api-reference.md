# API reference generated from the packages on every build (human asked; details agent)

- Human: the docs site has an API reference generated from the packages' public exports, types and JSDoc, regenerated on each build so it can't drift from the code.
- **Generated with the TypeScript compiler API** (`typescript6`, the one Twoslash already runs on), in `www/build/api-reference.ts`: for each package in `packages/` that isn't private, each `exports` entry (a condition object resolves through `types`, `import`, `default`), its exports and the members of the namespaces it exports (`export * as Loader`). Nothing names a package, file or export: an entrypoint, rename or new export shows up on the next build.
- **Signatures come from declaration emit**: the program emits `.d.ts` in memory and each export shows its statements from there, so inferred types are filled in and written annotations stay as written. Interface members keep their JSDoc; oxfmt formats each signature at 72 columns.
- **Pages are markdown fed through the same pipeline as `www/content`** (`www/build/api-pages.ts`): an index (`/docs/api`) and a page per entrypoint (`/docs/api-<specifier>`), in the `API reference` sidebar section. They get the layout, table of contents, search, `.md` URLs, `llms.txt`, social cards and sitemap with no code of their own. They have no file, so `virtual:docs-api` serves them; a package change in dev regenerates them.
- **Anchors are the names**: `#useAtomResult`, `#Loader.ensure`, from a heading's trailing `{#id}` (`remarkHeadingIds`). A flat module's group is `#module-<file>`.
- **The guides link API names**: inline code naming an export (`useAtomResult`, `Loader.ensure()`, `<AtomErrorBoundary>`) links to its anchor at its first mention on a page (per section on the reference's own pages). A package's main entry beats its subpaths, an export by its own name beats a namespace member by its short name, and a name whose best match isn't unique isn't linked. A lone lowercase word (`fetch`, `ensure`) isn't auto-linked: it's as often the browser's `fetch` or a verb in prose, so a page links those by hand (the verbs table in `loader-verbs.md`).
- **The build fails on a link to a page or heading that doesn't exist**, and on two headings with one id, so a hand-written link to an anchor breaks the build when the export goes.
- **JSDoc check**: `www/build/api-reference.test.ts` fails CI when a public export has no JSDoc description. The build only warns, so a missing comment doesn't stop a deploy.
- **Search**: the reference's pages weigh 0.3 of a guide's, so a guide about a word ranks above the exports whose names hold it, and a query that spells an API name (`useAtomResult`, `Loader.make`) puts that export first.
- There was no handwritten API reference to replace.
- Lost: TypeDoc (its own site and theme, or JSON we'd still have to render; and it needs the `typescript` package, which is TypeScript 7 here, with no JavaScript API), Twoslash per signature (a declaration isn't a compilable block, and hovers on a signature add little), and examples compiled with Twoslash (JSDoc examples lean on context they don't import, so they're highlighted only).
