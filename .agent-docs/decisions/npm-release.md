# npm release path (human: release on every push that changes a package)

- release-it + GitHub Actions, run from the repo root with one config per package (`release-it/<package>.json`, `.github/workflows/release.yaml`). Setup steps live in `.github/DEVELOPMENT.md`.
- **The Release workflow runs after CI passes on a push to `main`** (`workflow_run` on CI, `conclusion == success`, `event == push`), and by hand (`workflow_dispatch`). Human (2026-10-23): publish automatically, without slowing down breaking changes or pushing straight to `main`. Agents still never run release-it (not even `--dry-run`) or `npm publish`.
- **Only the commit CI checked is released**: the gate skips when `main` moved past `workflow_run.head_sha`, and each release job skips when `main` has commits past the gate's other than `chore(release)`. A plain `push` trigger lost because it would publish before (or despite) a red CI. The newer commit's own CI run releases instead.
- **Pushes with the workflow's `GITHUB_TOKEN`**, not a PAT: `main` is unprotected, and a `GITHUB_TOKEN` push doesn't start CI, so the release commit can't loop back into Release. Adding branch protection or a ruleset means going back to a PAT that can bypass it.
- **A package not on npm yet is skipped with a warning** (`npm view` E404) instead of failing every push until the one-time setup is done.
- **Each package versions on its own** (human): its tag is `<package>@x.y.z` (`git.tagName`, and `tagPrefix` for the changelog's bump), its notes go to `packages/<package>/CHANGELOG.md`, and the release commit is `chore(release): <package>@x.y.z`. The gate makes a matrix of the packages with commits since their own tag; the jobs run one at a time because each pushes to `main`.
- `npm: false` in release-it: the **package's latest tag is the version source**, `0.0.0` before its first one; `after:bump` writes the version into that package's `package.json`.
- **Publish before git**: `before:git:release` builds the package, checks `main` hasn't moved ([release-skips-stale-main.md](./release-skips-stale-main.md)), then runs its `publish:npm` (`pnpm pack`, whose `prepack` copies the root `LICENSE` in, then `npm publish`), so a failed publish pushes no commit or tag. CI's Pack Check packs the same way on every push ([pack-check.md](./pack-check.md)). The changelog is already written by then (the plugin's `beforeRelease`), and on a package's first release the plugin generates its whole history.
- The configs are full copies, not `extends` of a shared base: c12 (release-it's loader) resolves a relative `extends` against the working directory and then imports it relative to the config file, so `./release-it/base.json` can't load. `tooling/conventional-commits`' `release-config.test.ts` keeps them in sync.
- Publishes via npm OIDC trusted publishing (`id-token: write`, empty `NODE_AUTH_TOKEN`). npm only allows a trusted publisher on a package that exists, so each package needs one manual first publish (`--provenance=false`) before `npm trust github`. `npm publish` from an agent shell fails with `EOTP` anyway.
- **The docs site's announcement bar is set by hand**: `www/src/components/announcement-bar.tsx` shows `announcements.onNpm` (on npm, pre-1.0 so minors can break, a link to Installation) since both packages' first release (0.1.0, 2026-10-23). release-it doesn't touch it, so a release that changes what it should say (a 1.0, say) has to change it too.
- Before the first release, check both names (and punctuation variants such as `raf-effectatom`, `effect-atom-boundaries`, `@effect-atom/boundary`) are still free on npm. On 2026-10-23 `raf-effect-atom` and `effect-atom-boundary` were.
